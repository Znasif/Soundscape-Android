# Architecture & Design Decisions

All open design questions are resolved conservatively and recorded below.

| ID | Step | Question | Chosen Default | Reason |
|---|---|---|---|---|
| **D-01** | 0 | How should `perception/` be structured as a Gradle build without touching root build files or triggering the Android plugin? | Standalone Gradle build in `perception/` with its own `perception/settings.gradle.kts` (`rootProject.name = "perception"`) and `perception/build.gradle.kts` using Kotlin/JVM `2.4.21`, invoked via `./gradlew -p perception test`. | Isolates JVM perception code completely from the Android SDK (which is absent in the sandbox) while reusing the repo's Gradle wrapper and library versions (`Kotlin 2.4.21`, `Ktor 3.5.1`, `Coroutines 1.11.0`, `JUnit 6.1.2`). |
| **D-02** | 0 | Should we implement live GeoParquet HTTP range fetching for Overture Maps in Step 2? | Define `OvertureClient` as a pure Kotlin interface in `sim/sources` with a documented stub/TODO and use `OverpassClient` + `MapillaryClient` for live outdoor geometry and POIs. | Overture distributes multi-GB cloud GeoParquet files; parsing Parquet footers and column chunks without DuckDB or heavy Apache Parquet/Hadoop dependencies is impractical for a lightweight mobile library, and standard Overture `places`/`buildings` schemas (`v2.0.0`) do not expose separate entrance point coordinates (`https://docs.overturemaps.org/schema/reference/places/place/`). |
| **D-03** | 0 | Which hosted models and endpoints should be used for segmentation, verification/OCR, and embeddings? | Meta `sam-3.1` via `POST https://api.meta.ai/v1/responses` for segmentation; Google `gemini-3.8-flash` (with `thinkingBudget = 0`) via `POST .../v1beta/models/gemini-3.8-flash:generateContent` for crop verification & OCR; `gemini-embedding-2-preview` via `:embedContent` for room image embeddings (with deterministic local feature fallback when offline). | Verified live in Step 0 probes: `sam-3.1` returns bounding boxes and `one_bit` base85 masks at `$0.0025`/image (`2.56 s`), and `gemini-3.8-flash` provides low-cost stateless vision verification and OCR without Meta Contributor-tier data-sharing trade-offs. |
| **D-04** | 0 | How should CC-BY-NC datasets/models (Boxer, OrienterNet, MGL, ScanNet++, 3RScan, Aria ASE/EFM3D) and Mapillary images be handled? | Exclude all CC-BY-NC / non-commercial models and datasets from code paths; never commit raw Mapillary images or un-scrubbed signed URLs; commit only derived JSON manifests with `Mapillary (CC-BY-SA)` and `OpenStreetMap (ODbL)` attribution. | Respects licensing and privacy rules (`https://www.mapillary.com/developer/api-documentation`, `https://www.projectaria.com/datasets/ase/license/`). |
| **D-05** | 1 | What local Cartesian coordinate convention and quaternion ordering should `sim/geo` and `sim/model` use? | Local coordinates: `[east, up, north]` in `SimObject.position` (`[x, y, z]` where `x = East (m)`, `y = Up (m)`, `z = North (m)`, matching Y-up glTF / XR Blocks convention while keeping 2D ground operations in `(east, north)`). Quaternions: scalar-first `(w, x, y, z)` in `Quaternion` math (`sim/geo`) matching Meta Wearables DAT `MotionSample`, serialized as `[x, y, z, w]` in `SimObject.quaternion` for XR Blocks compatibility. | Aligns internal 6-DoF/3-DoF rotation math with Meta Wearables DAT (`w, x, y, z`) and compass bearings (`0° = North (+Z)`, `90° = East (+X)`, `y = Up`) while preserving XR Blocks manifest compatibility. |
| **D-06** | 1 | What camera height and minimum pitch below horizon should be used for monocular ground-plane distance (`d = h / tan(pitch_below_horizon)`)? | Default eye/glasses height `h = 1.65 m` (configurable per builder/test); reject rays with `pitch_below_horizon < 4.0°` (`d > ~23.6 m`) as near/above-horizon. | Prevents near-horizon `1 / tan(pitch)` blow-up from small IMU pitch errors during head-turn room scans. |
| **D-07** | 2 | How should Overpass queries be scoped to avoid timeouts and HTTP 429/504 errors on dense city blocks? | Query `way["building"]`, `relation["building"]`, `node["entrance"]`, `node["name"]`, and `way["name"]["highway"!~".*"]` within `around:R,lat,lon` using `[timeout:25][out:json]`, omitting general `relation["name"]` which pulls full-city transit/route geometries. | Verified in Step 0 Probe 2 on Ferry Building: excluding route relations returned all 2 buildings, 9 entrances, and 50 named POIs cleanly in one JSON response. |
| **D-08** | 3 | How should SAM 3.1 text prompts be issued for multiple categories (`door`, `shop sign`, `steps`)? | Issue one short noun-phrase prompt per `sam-3.1` request (`"door"`, `"shop sign"`, `"steps"`) on selected facade-facing perspective crops, gated by `Budget` caps (`--max-sam-calls`, default 60). | Meta SAM 3.1 documentation (`https://dev.meta.ai/docs/sam/segmenting`) specifies that text prompts must be a single short noun phrase per call rather than comma-separated lists. |
| **D-09** | 4 | How should `RoomRecognizer` prevent false matches between visually similar rooms (e.g., "Room 214" vs "Room 216")? | Combine visual embedding cosine similarity with a hard discriminative check on extracted room/door number tokens: if both stored and query scans contain distinct alphanumeric identifiers (e.g. `214` vs `216`), force a non-match regardless of visual similarity, and require overall similarity `>= 0.80` to match (otherwise abstain). | Guarantees zero false matches on near-duplicate rooms while allowing recognition under yaw offsets and furniture movement. |
| **D-10** | 3 | How should elevated plaza canopies (`building=roof`, e.g., `way/1189071405` in front of the Ferry Building) be handled during facade ray intersection? | Filter out `building=roof` / `building=canopy` polygons when walled buildings exist in the same area. | Prevents facade-facing camera rays from prematurely terminating on an open-air transit canopy 18 m in front of the actual Ferry Building wall (`way/558731934`). |
| **D-11** | 3 | How should open 2-wing hinged double doors (`door:wings=2`) be localised when `sam-3.1` segments the left and right glass leaves separately? | Pair co-horizontal door wings in `MetaSam31Client.mergeDoubleDoorWings` when vertical bounds (`y1`, `y2`) align within `25 px` and horizontal separation is `<= 140 px`. | Places the merged bounding-box bottom-centre at the true doorway threshold centreline (`2.87 m` error on Ferry Building entrance `11041574557` instead of `7.5 m` on an outer wing). |
| **D-12** | 5 | What are the verified geocoded coordinates and OSM identifiers for the owner's research institute at `2318 Fillmore Street, San Francisco`? | Building footprint `way/160705972` (`name="The Smith-Kettlewell Eye Research Institute"`, `addr:housenumber=2318`, `addr:street="Fillmore Street"`, `wikidata=Q30279651`, centroid `37.7911743, -122.4339323`) and western-facade office POI `node/13639682002` (`37.7911624, -122.4341427`, `name="Smith-Kettlewell Eye Research Institute"`, `office=research`, `wheelchair=yes`), between Clay St and Washington St. Nearest Fillmore Muni stops: `node/6368210990` (`Fillmore St & Sacramento St`, ref `14637`, `37.7899894, -122.4341405`) and `node/6368210995` (`Fillmore St & Jackson St`, ref `14624`, `37.7922243, -122.4346215`), plus `node/6384667509` (`Washington St & Fillmore St`, ref `16916`, `37.7915282, -122.434526`). | Verified via Nominatim (`place_id=323196953`, `place_id=323144522`) and OpenStreetMap API v0.6 (`map.json`). Notably, `way/160705972` has zero `entrance=*` nodes in OSM, making it an ideal real-world test of perception adding entrances that OSM lacks. |
| **D-13** | 5 | Which 10 evaluation areas (2 development + 8 held-out) are pre-registered before running perception in Step 5c? | **Criteria**: radius `60–75 m` (`185 m` for the full Fillmore corridor), `>= 5` OSM `entrance=*` nodes on building footprints, `>= 1` Mapillary 360° `is_pano` image captured within the last 5 years within `40 m` of facades, and all held-out areas `> 1 km` from Fillmore across `7` cities and `3` countries (USA, UK, France). **Development (2)**: `ferry-building` (`37.79545, -122.39373`, SF, USA) and `fillmore-2318` (`37.791174, -122.433932`, SF, USA). **Held-out (8)**: `sf-caltrain-4th-king` (`37.7766, -122.3948`, SF, USA, `3.8 km` from Fillmore), `nyc-grand-central` (`40.7524, -73.9774`, NYC, USA), `boston-south-station` (`42.3521, -71.0553`, Boston, USA), `chicago-union-station` (`41.8789, -87.6395`, Chicago, USA), `seattle-king-street` (`47.5984, -122.3299`, Seattle, USA), `london-st-pancras` (`51.5301, -0.1252`, London, UK), `paris-gare-du-nord` (`48.8802, 2.3553`, Paris, France), `paris-chatelet` (`48.8584, 2.3475`, Paris, France). | Pre-registered in `DECISIONS.md` prior to running perception on any held-out area so evaluation parameters are frozen on the 2 development areas first. |
